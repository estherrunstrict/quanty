# Decision Approval Buttons — Design Spec

- **Date:** 2026-06-03
- **Author:** Claude (with Jae)
- **Status:** Approved design → ready for implementation plan
- **Approach:** A (public dashboard buttons → Cloudflare Tunnel HTTPS → token-gated host endpoint), with the **quick-tunnel / ephemeral-URL** variant (no domain).

## Goal

Let Jae **approve or reject open decision memos** with a button on the public Quanty dashboard, instead of hand-editing wiki markdown frontmatter. The button **records** the decision (flips memo `status: proposed → approved|rejected`) — it never executes the underlying action. Execution stays a separate Claude+Jae step, honoring the hard rule.

## Non-goals

- No auto-execution of decisions (deploy/retire/allocate). The button only flips status.
- No new-decision authoring, no per-bot verdict editing (separate future features).
- No change to live trading code, `check_and_run.sh`, or the trading cron.
- Not a high-availability service — quick tunnels are best-effort; approvals are infrequent.

## Context

- Open memos surface in `decisions.json` under `open_decisions` (3 today), generated by `generate_decisions_json.py` from memo frontmatter in `/home/ubuntu/quanty-wiki/wiki/decisions/*.md` (`status: proposed`).
- The public Decision Center (`https://estherrunstrict.github.io/quanty/decision.html`, source `wiki/dashboard/index.html`) is a **static** GitHub Pages page that fetches `data/decisions.json`.
- `decisions.json` is published to Pages by the `push_dashboard.sh` cron (16:00 / 06:30 KST) from `/home/ubuntu/quanty-dashboard/docs/data/`.
- The host (`193.123.246.52`) also runs the live trading bots + brokerage creds, has **no TLS / no domain**, and only `:8077` (plain HTTP) listens. So the write path must not expose the host directly.

## Architecture & data flow

```
Jae's browser  (GitHub Pages: decision.html)
   │  click Approve/Reject on an open memo → confirm → bearer token
   │  1. GET  data/approve_endpoint.json   (current tunnel URL, no-store)
   ▼  2. POST <tunnel-url>/approve  {id, action}   Authorization: Bearer <token>
cloudflared  (quick tunnel, HTTPS, OUTBOUND — no inbound port opened)
   ▼  → 127.0.0.1:8078
decision_approval_server.py  (systemd, localhost-only)
   ├─ validate: token (constant-time) · action∈{approve,reject} · memo exists & status==proposed
   ├─ edit  /home/ubuntu/quanty-wiki/wiki/decisions/<id>.md   status→approved|rejected (+ approved_by, approved_at, updated)
   ├─ run   generate_decisions_json.py  → /home/ubuntu/quanty-dashboard/docs/data/decisions.json
   ├─ git -C quanty-dashboard add/commit/push docs/data/decisions.json   → Pages updates (~1 min)
   ├─ (if quanty-wiki is git-backed) commit the memo there for history
   ├─ append audit log line
   └─ 200 {ok, id, new_status}
browser: optimistic row update + toast; next decisions.json fetch confirms
```

## Components

### 1. `decision_approval_server.py` (new, in `quanty-dashboard/`)

A small **standalone** service — deliberately NOT folded into the read-only `dashboard_server.py`, because this is a write path touching the wiki + git push (higher-risk, separate concern).

- Stdlib `http.server`, bound to **`127.0.0.1:8078`** only (unreachable except via cloudflared).
- Routes:
  - `OPTIONS /approve` → CORS preflight (allow the Pages origin + `Authorization`, `Content-Type`).
  - `POST /approve` body `{"id": "<memo-slug>", "action": "approve"|"reject"}`.
- Request handling (tight whitelist — even a leaked token can only flip a proposed memo):
  1. **Auth**: `Authorization: Bearer <token>`; constant-time compare against the secret loaded from a service-only file (`APPROVAL_TOKEN_FILE`). Missing/wrong → `401`.
  2. **Rate limit**: in-memory token-bucket, ≤10 requests/min per process → `429` on exceed.
  3. **Validate action** ∈ {approve, reject}, else `400`.
  4. **Resolve memo**: `id` maps to `<DECISIONS_DIR>/<id>.md`; `id` must match `^[a-z0-9-]+$` (no path traversal). Not found → `404`.
  5. **State check**: parse frontmatter; current `status` must be `proposed`, else `409` (already decided).
  6. **Apply**: rewrite frontmatter `status: proposed → approved|rejected`, set `updated: <ET today>`, add `approved_by: jae`, `approved_at: <iso>`. Atomic write (tmp + `os.replace`).
  7. **Regenerate**: run `generate_decisions_json.py` with the same env `push_dashboard.sh` uses (`QUANTY_WIKI_DIR`, `QUANTY_AUTOMATION_DIR`, `QUANTY_DECISIONS_OUT`).
  8. **Publish**: `git -C /home/ubuntu/quanty-dashboard add docs/data/decisions.json && commit && push`. If quanty-wiki is a git repo, also commit the memo there.
  9. **Audit**: append `{ts, id, action, status, remote_ip, token_ok}` to `approval_audit.log`.
  10. Respond `200 {ok:true, id, new_status}`. On regenerate/push failure → `500` but the memo edit (source of truth) persists and the next cron republishes.
- The pure core `transition_frontmatter(content, action, now) -> new_content` and `current_status(content) -> str` are separate functions for unit testing.

### 2. `quanty-decision-approval.service` (systemd)

`Restart=always`, `ExecStart=/home/ubuntu/myenv/bin/python3 decision_approval_server.py`, `WorkingDirectory=/home/ubuntu/quanty-dashboard`, `User=ubuntu`, `Environment=APPROVAL_TOKEN_FILE=/home/ubuntu/.quanty_approval_token` and the `QUANTY_*` vars. Logs to a file like the dashboard unit.

### 3. cloudflared quick tunnel + URL publisher

- `start_approval_tunnel.sh` (new): runs `cloudflared tunnel --url http://localhost:8078`, watches its output for the `https://<rand>.trycloudflare.com` line, and on capture writes `/home/ubuntu/quanty-dashboard/docs/data/approve_endpoint.json` = `{"url": "<tunnel>", "updated_at": "<iso>"}`, then `git add/commit/push` that file. Keeps cloudflared in the foreground (so systemd supervises it); re-publishes if the URL line reappears.
- `quanty-approval-tunnel.service` (systemd, `Restart=always`) runs the wrapper. No Cloudflare account/login needed for quick tunnels.
- **Quick-tunnel caveat** documented in the runbook: URL is ephemeral (changes on restart, ~1 min Pages-lag to republish) and best-effort. Upgrade path to a named tunnel + domain is drop-in (only the wrapper changes; server/frontend unchanged).

### 4. Frontend — buttons in `wiki/dashboard/index.html` (→ `decision.html`)

- In the `open_decisions` render, add **Approve** / **Reject** buttons per memo.
- Click handler: `confirm()` dialog → ensure token (prompt once via `prompt()`, store in `localStorage['quanty_approval_token']`) → `GET data/approve_endpoint.json` (no-store) → `POST <url>/approve` with the bearer header and `{id, action}`.
- On `200`: grey out the row, show new status + toast. On `401`: clear stored token + "token rejected". On `409`: "already decided — refresh". On network/`5xx`/missing endpoint: "tunnel may be restarting, try again shortly".
- Vanilla `fetch`, matching the dashboard's existing style — no build tooling.

### 5. Token provisioning & security

- Token: `openssl rand -hex 32` → `/home/ubuntu/.quanty_approval_token` (chmod 600, `ubuntu`-only). Jae enters it in the browser once.
- Transport: HTTPS via the tunnel (encrypted). Local service bound to `127.0.0.1` only.
- CORS limited to `https://estherrunstrict.github.io`.
- Whitelist (action ∈ approve/reject, id regex, status must be proposed) + rate limit + audit log.
- Blast radius even if token leaks: flip proposed memos to approved/rejected — no money movement, no code exec, no execution of the decision.

## Error handling

- `400` bad action/body · `401` bad token · `404` unknown memo · `409` not proposed · `429` rate-limited · `500` regenerate/push failure (memo edit still persisted; cron will republish).
- Partial-failure rule: the memo file is the source of truth. If regenerate or push fails after the edit, log it and return `500`; the dashboard will reflect the change on the next cron push even without an immediate push.
- CORS preflight handled explicitly so the cross-origin POST works.

## Testing

- **Unit** (`tests/test_decision_approval.py`): `current_status` parsing; `transition_frontmatter` for approve, reject, and idempotency (already-approved input → raises/flagged); `id` regex rejects traversal; token compare; action whitelist. The transition is a pure `(content, action, now) → content` function.
- **Integration**: start the server on a temp port with a fixture memo + test token; assert `401` (no token), `409` (already decided), `200` (proposed→approved) and that the file changed. Stub the git push in tests.
- **Manual**: buttons render; click → endpoint fetch → POST → row updates; reject path; expired-tunnel message.

## Deployment / rollout

- New files land in `quanty-dashboard/` (server, wrapper, tests) + the systemd units + the frontend edit. Deploy via the existing `scp` + `push_dashboard.sh` flow; extend `deploy_dashboard.sh` if convenient.
- One-time (Jae, sudo): install `cloudflared`; generate the token file; install + enable both systemd units; confirm `approve_endpoint.json` publishes.
- Runbook: `automation_oracle/docs/runbooks/decision-approval.md` (token gen, cloudflared install, unit install, verify, quick-tunnel caveat, named-tunnel upgrade path).
- Isolation preserved: no `*AutoTrade*.py`, no `check_and_run.sh`, no trading cron touched.

## Future work

- Named tunnel + domain for a stable URL (drop-in replacement of the wrapper).
- Extend to per-bot verdict buttons and new-decision authoring once the approve/reject path is proven.
